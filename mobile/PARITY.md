# Паритет «сайт ↔ приложения» (CRM 1.15.0, клиент — v1 в разработке, 25.11.2026)

Два приложения из одной кодовой базы — CRM для сотрудников и «MyBooks» для авторов (mobile/CLIENT-APP.md).

Новые экраны CRM берут данные только из контракта API v1 (`packages/contracts/src/v1/crm*.ts`, ADR 0012), не из ручных
маршрутов. Порядок переноса со страниц CRM — по частоте: правка сделки и клиента, бот (1.5.0) → деньги и трек заказа (1.5.2) → доски (1.6.0) → файлы
заказа, обращения, новый клиент со сделкой (1.7.0) → правка получателя и пересборка файлов (1.7.1) → финансы, расходы, прибыль (1.8.0) → реестр продаж, аналитика и статистика лидов (1.9.0) → отдел продаж и AI-продажник, CRM-страницы с шапкой приложения (1.10.0) → маркетинг (1.11.0) → книги и каталог WhatsApp (1.12.0) → сделка, клиент и заказ без «Открыть в CRM» (1.13.0) → фильтры воронки и заказов, вложения и ссылки — своими экранами (1.14.0) → команда, общие шаблоны, цены, сайт; у разделов из «Ещё» название и кнопки — в шапке рядом с «назад», без пустой полосы (1.15.0) → перевод списков, сторов, карточек и мутаций CRM на API v1 (ETag/304 + `LocalCache`), нативные «Почему так?» бота (ответы и молчание), КП, роли и 2FA (25.11). Страницами CRM (с шапкой приложения) остались только редакторы настроек и чат CRM для звонка WhatsApp.

Правило: что продажник и руководитель делают каждый день — экраном приложения; остальное открывается **страницей CRM
внутри приложения** (встроенный браузер `CrmWebScreen`, уже вошедшим: `authWebSession` в API v1 — отдельная
сессия, «Выйти» на сайте не закрывает приложение). Права везде те же, что на сайте: экраны приложения ходят в те же
server actions (`assertStaff`, роли), страницы — это сам сайт. Дыр нет: каждая страница боковой панели CRM доступна.

Обозначения: **экран** — своё в приложении; **CRM** — страница CRM во встроенном браузере (кнопка ↗ «Открыть в CRM» или
раздел в «Профиле» / «Ещё»); **≈** — работает иначе, чем на сайте.

## Дизайн

Палитра и тёмная тема — `html.crm` (`lib/ui/tokens.dart`), винная главная кнопка, rose — свои сообщения, info — бот,
аватары тонами CRM, экран входа как CRM. Страницы CRM во встроенном браузере — это сам сайт (его тема).

## Что работает иначе

- Канбан заказов и доска сделок на телефоне — списки по статусам с фильтрами (как мобильная вёрстка сайта); перетаскивание заменяет «Сменить статус» / «Перенести».
- Звонок WhatsApp — через страницу CRM внутри приложения, а не нативный экран звонка.
- iPhone ставится не из App Store: регистрация телефона на `/admin/app` и установка по ссылке (Ad Hoc).

## Что осталось страницей CRM в приложении (с 1.15.0) и почему

Все такие страницы открываются с шапкой приложения (назад и название), без верхней полосы CRM.

| Что | Почему не экраном |
|---|---|
| Автоматизации | редактор правил «событие → условия → действия» с ветвлениями — не для телефона |
| Интеграции (ключи Kaspi, WhatsApp, почта, телефония, AI; тексты и вопросы бота, стоп-лист, праздники) | ключи и пошаговые настройки интеграций; режим AI-продажника — экраном («Отдел продаж») |
| Лимиты AI | окна и пороги по каждому инструменту и по клиенту — таблица на десятки чисел |
| Планы продаж (из «Команды») | таблица плана по месяцам; сотрудники и роли с правами — экраном |
| Модели ИИ-дизайнера | выбор модели под каждый сценарий; статистика и лимит — экраном |
| Загрузка APK (в «Сайте») | файл с компьютера |
| Чат: звонок WhatsApp (меню чата → «Позвонить в WhatsApp») | звонок — см. ниже; «Почему так?» и КП — экраном |
| Предпросмотр книги и упаковочный лист (меню заказа) | документы сайта (книга, печатный бланк), не страницы CRM |

## Звонок WhatsApp нативно — что нужно

Сейчас звонок идёт в чате CRM внутри приложения (WebRTC браузера не нужен: звук — WebSocket `/wa-call/audio` с кадрами
шлюза, nginx пускает по сессии через `/api/admin/calls/whatsapp/audio-auth`; сигналы — `POST /api/admin/calls/whatsapp/<id>`
heartbeat/connected/hangup/ended; запись — кусками в `/recording`). Для своего экрана звонка:

1. Звук: захват микрофона PCM 16 бит с эхоподавлением (iOS voiceProcessing / Android VOICE_COMMUNICATION), пересчёт в
   кадры шлюза (как MicEncoder в `src/components/admin/wa-call/engine.ts`), проигрывание PCM с джиттер-буфером (логика —
   `public/wa-call-worklet.js`) — нужен плагин низкой задержки (свой platform channel или flutter_pcm_sound).
2. Сессия и сигналы: WebSocket с Bearer (audio-auth уже принимает `apiStaff`), heartbeat, восстановление (RETRY_MS),
   запись разговора кусками.
3. Системный экран: CallKit (iOS) и ConnectionService (Android) — плагин уровня flutter_callkit_incoming; фоновый звук
   (UIBackgroundModes audio, voip).
4. Входящий при закрытом приложении: VoIP-push (PushKit, apns-push-type voip, тема `<bundle>.voip`) с сервера — новый
   вид push в `src/server/push`; на Android — высокоприоритетный FCM (ключи FCM на проде ещё не заданы).
5. Проверка — только на реальных телефонах с живым номером WhatsApp (в симуляторе нет ни шлюза, ни нормального микрофона).

Оценка: отдельная работа на несколько дней с проверкой на устройствах; за один заход без проверки выпускать нельзя —
сломанный звонок хуже звонка в CRM.
