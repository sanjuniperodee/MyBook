# Архитектура MyBooks

Модульный монолит на Next.js с DDD и слоистой (чистой) архитектурой. Документ — обязательное чтение перед изменением серверного кода.

## Почему так

- **Бизнес-правила живут в одном месте.** Цена заказа, переходы статусов, правила промокодов находятся в агрегатах. Их не размазывают по server actions, страницам и роутам.
- **Контексты не знают друг о друге.** «Заказы» публикуют событие «заказ оплачен». CRM, письма и производство подписываются на него сами. Добавить реакцию на событие можно, не трогая заказы.
- **Тестируемость.** Домен и сценарии проверяются юнит-тестами на репозиториях в памяти, без БД и браузера (`tests/ordering.test.ts`, `tests/authoring.test.ts`, `tests/identity-access.test.ts`).
- **Заменяемая инфраструктура.** Можно поменять Postgres на другую БД, SMTP на API-рассылку или CloudPayments на Kaspi. Это меняет адаптер, а не бизнес-логику.

## Слои

```
src/
  shared/                     общее ядро (shared kernel)
    domain/                   Entity, AggregateRoot, ValueObject, DomainEvent, DomainError
    application/              UseCase, UnitOfWork, EventBus, Clock, Logger, Mailer, RateLimiter — порты
    infrastructure/           db/ (схема Drizzle, пул, миграции), database.ts (executor() — текущая транзакция или пул),
                              DrizzleUnitOfWork (транзакции), OutboxDispatcher (надёжная доставка событий), InProcessEventBus,
                              redis.ts (лимиты и шаги TOTP: Redis при REDIS_URL, иначе память), background.ts,
                              mail.ts (SMTP-адаптер Mailer и общий HTML-шаблон писем), storage.ts (файлы)
  modules/<контекст>/
    domain/                   агрегаты, объекты-значения, события, ошибки, интерфейсы репозиториев
    application/              сервисы сценариев (команды), порты к другим контекстам и внешнему миру
    infrastructure/           репозитории Drizzle, read-модели, адаптеры (почта, платежи, PDF), подписчики
    ui/                       чистые помощники для интерфейса (подписи статусов, цвета) — можно в клиентских компонентах
    index.ts                  публичный фасад модуля — единственная точка входа для остального кода
  server/
    container.ts              корень композиции: собирает модули из реализаций (DI без магии и декораторов)
    subscriptions.ts          связи между контекстами через доменные события
    auth.ts, access.ts        веб-адаптеры: cookie сессии и билета 2FA, guards сотрудников (requireStaff, assertStaff…)
    books.ts                  веб-адаптер книг: книга, доступная текущему пользователю (404 для чужой)
    api.ts, rateLimit.ts      обёртка роутов (ошибки домена → HTTP, права), лимиты частоты по IP
    track.ts, scheduler.ts    события аналитики в cookie; фоновые задачи (автописьма, правила CRM, outbox, почта IMAP)
  config/                     справочники каталога (site.ts: тарифы, доставка) и переменные окружения (env.ts)
  lib/                        чистые библиотеки без БД и модулей: вёрстка книги (book/), банк вопросов и SEO-тексты (content/),
                              поводы и сроки (occasions.ts), помощники интерфейса (utils, client-api, csv)
  app/                        слой представления: страницы, server actions, роуты — тонкие контроллеры
```

Зависимости направлены внутрь: `app → server/container → modules/*/index → application → domain`. Домен не зависит ни от чего, кроме `shared/domain` и справочников каталога (`config/site`).

### Правила, которые проверяет линтер (`eslint.config.mjs`)

| Слой | Нельзя импортировать |
|---|---|
| `modules/*/domain` | drizzle, `shared/infrastructure`, Next.js/React, `server-only`, application/infrastructure |
| `modules/*/application` | drizzle, `shared/infrastructure`, Next.js/React, infrastructure, `server/*` |
| `modules/X/**` | `application`/`infrastructure` другого модуля — только его `index.ts`, `domain` или `ui` |
| `app/**`, `components/**` | `application`/`infrastructure` модулей, `shared/infrastructure`, drizzle и `pg`: страницы и действия не ходят в БД |
| `lib/**` | drizzle, `pg`, `server-only`, `server/*`, модули, `shared/infrastructure` (кроме типов строк из `db/schema`) |

Динамический `import()` линтер не проверяет — для него действует то же правило: чужой модуль только через фасад (пример — `renderGiftPdf` в `@/modules/production`).

## Строительные блоки

- **Агрегат** (`AggregateRoot`) — граница согласованности. Состояние меняется только его методами (`order.markPaid()`, `order.cancel()`). Методы проверяют инварианты, пишут журнал и записывают доменные события.
- **Репозиторий** — интерфейс в `domain/repositories.ts`, реализация на Drizzle в `infrastructure/persistence`. Мапперы переводят строку БД в агрегат и обратно. Атомарные операции, которым нужна БД (резерв использования промокода `tryReserve`), объявлены методами репозитория.
- **Сервис сценариев** (`OrdersService`, `PromoService`, `GiftsService`) — оркестрация: загрузить агрегат, вызвать метод, сохранить. Каждая команда выполняется в `uow.run()`, то есть в одной транзакции.
- **Unit of Work.** `uow.run()` открывает транзакцию, репозитории берут её через `executor()` (AsyncLocalStorage). После COMMIT события агрегатов из `uow.track()` публикуются в шину. При откате события не публикуются.
- **Доменные события** — факты в прошедшем времени: `ordering.order_paid`. Они записываются в **transactional outbox** (`outbox_events`) в той же транзакции. После COMMIT событие доставляется сразу, а если подписчик упал или процесс перезапустился — его досылает воркер, вызывая только тех подписчиков, кто ещё не отработал. Имя подписчика обязательно и стабильно. Подробности и почему без Kafka/RabbitMQ — [ADR 0001](adr/0001-messaging-queues-cache.md).
- **Ошибки домена проверяются через `XError.is(err)`, а не `instanceof`.** Next.js загружает модули в разные слои бандла (страницы, server actions), и классы там — разные экземпляры.
- **Порты к другим контекстам** (`BookGateway`, `PeopleGateway`, `PrintFiles`) объявляются потребителем в `application/ports.ts`. Реализация — антикоррупционный слой в `infrastructure/gateways`.
- **Read-модели (CQRS-lite).** Экранам не нужны агрегаты. Запросы для страниц одного контекста лежат в его `infrastructure/**/*Queries.ts` (`container().authoring.queries`, `container().messaging.queries`). Экраны, которые собирают данные нескольких контекстов (дашборд, «Мой день», карточки сделки и клиента, списки, инбокс, аналитика), читают модуль `reporting` — он только читает и ничего не меняет. Видимость «только свои» передаётся как `Viewer { userId, seesAll }` или `StaffContext`. Рендер PDF тоже получает книгу из read-модели Authoring — производство не читает таблицы книг само.
- **Ошибки домена** — `DomainError` со стабильным `code`. Код совпадает с ключом словаря, и слой представления показывает текст на языке пользователя.

## Как добавить фичу

1. Правило бизнеса оформляется методом агрегата (или новым агрегатом) и юнит-тестом на него.
2. Сценарий — метод сервиса в `application`. Нужен другой контекст — объявите порт в `ports.ts`.
3. Хранение — метод репозитория и его реализация на Drizzle. Схема меняется через миграцию (`npm run db:generate`).
4. Реакции других контекстов — подписка в `server/subscriptions.ts` (или в фасаде модуля, если это собственная реакция).
5. Server action или роут: проверить права, разобрать ввод через zod, вызвать `container().<модуль>.<сервис>.<команда>()`, перевести `DomainError` в текст.
