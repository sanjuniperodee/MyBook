# Счёт из чата и доступ в кабинет после оплаты

Менеджер прямо в переписке с клиентом выставляет счёт по сделке. Клиент платит по ссылке `/pay/<token>`: Kaspi (счёт на номер или QR), карта (если подключена), перевод по реквизитам. После оплаты деньги записываются в сделку, менеджер получает уведомление, клиенту в тот же WhatsApp-чат уходит доступ в кабинет.

Вместе с этим: реквизиты перевода настраиваются в «Интеграциях» (на проде клиенты видят заглушку «+7 700 000 00 00»), голосовые и вложения WhatsApp открываются в CRM.

## 0. Сценарий целиком (решение владельца 16.10: клиент заводится оплатой)

1. **Счёт.** Менеджер в чате или сделке → «Счёт». Форма: имя клиента, язык кабинета, откуда пришёл, тариф и цена
   договорённости, сколько платить сейчас (предоплата 50% / полная / своя сумма). Телефон — номер WhatsApp-чата
   (сервер, менеджер его не видит). Договорённость сразу пишется в сделку; цена ниже прайса больше, чем на
   `crm.maxDiscount` %, — только руководитель (иначе «левак» заниженной ценой). Один открытый счёт на сделку.
2. **Оплата.** Клиент по ссылке `/pay/<token>`: Kaspi (счёт на номер или QR), карта, перевод по реквизитам компании.
   - Онлайн (Kaspi, карта) подтверждает платёжная система: платёж в сделке с операцией вместо чека, без участия менеджера.
   - Перевод: клиент жмёт «Я оплатил(а)» → задача ответственному; «Оплата пришла» в счёте — только с чеком.
     Ручное подтверждение помечается «проверить» в «Финансах», руководитель видит чек и отмечает «проверено».
3. **Клиент заводится оплатой** (в той же транзакции, что деньги): аккаунт с номером чата — ровно один → привязать;
   нет → создать (имя, язык, канал из счёта; ответственный — сделки); иначе (чужой `deal.clientId`, несколько
   совпадений, не WhatsApp) — никого не привязывать, задача менеджеру. Сделка и чат привязываются к клиенту, этап —
   «предоплата получена», заметка с условиями, задача «получить остаток N ₸», если оплачено меньше договорённости.
4. **Доступ** — ссылка «задайте пароль» на 72 ч в тот же чат на языке клиента (в CRM хранится замаскированной);
   уже пользуется кабинетом — «войдите как обычно». Один раз на сделку.
5. **Заказ.** Клиент пишет книгу и оформляет заказ: тариф и цена — по договорённости, внесённое вычитается,
   остаток — онлайн в заказе или постоплатой (`order-payments.md`). Заказ закрывает открытые счета сделки.
6. **«Финансы»** видят: пришло (по дням, способам, менеджерам), ожидается (договорённость − оплачено по открытым
   сделкам; отдельно — у кого книга готова), постоплаты по заказам, переплаты и возвраты, ручные подтверждения без проверки.

Дыры, которые закрыты явно: повторный платёж той же операции; оплата по закрытому/истёкшему счёту или после
заказа → «нужен возврат или зачёт», не теряется и не задваивается; переплата → задача; два счёта на сделку — нельзя;
чужой аккаунт по похожему номеру — не раскрывается; сделку с деньгами или открытым счётом нельзя удалить, слияние
переносит деньги и счета; менеджер не может подтвердить оплату без чека, занизить цену сверх лимита или удалить
онлайн-платёж; отмена заказа с предоплатой возвращает сделку в работу с деньгами.

Документ — спецификация. Учтены замечания состязательного ревью (деньги, безопасность, архитектура, продукт). Названия файлов и методов — ориентир; модули друг друга не импортируют, связи — портами в `src/server/container.ts`.

## 1. Деньги и договорённость

**1.1. Владелец счёта — ordering.** Новый агрегат `DealInvoice` («запрос оплаты по сделке»): ordering уже владеет платёжными системами (Kaspi `payment_invoices`, вебхук, сверка, CloudPayments) и страницей по токену (`/gift/[token]`). Деньги ordering отдаёт в sales портом в той же транзакции.

**1.2. Форма счёта требует договорённость целиком:** тариф (`agreed_plan`) и цену книги (`crm_deals.amount`). Обе сохраняются в сделку. Без тарифа договорённость стала бы потолком цены для любого тарифа (электронная за 9 900 → твёрдая за 9 900).

**1.3. Договорённость для сделок не «вручную».** `agreementForClient` и удержание предоплаты при отмене заказа (`SiteFunnelService.orderCancelled`, сейчас `held` только для `source='manual'`) используют один предикат продаж «сделка держит деньги клиента»: `source='manual' OR (agreed_plan IS NOT NULL AND EXISTS платежи сделки)`. Иначе оплаченная из чата предоплата не вычтется при оформлении, и клиент заплатит дважды.

**1.4. Сделка заказа — та, чья предоплата вычтена.** `agreementFor` уже знает `dealId`. Он попадает в `Order` (снимок) и в событие `ordering.order_placed` (`agreementDealId`); `sales.orderCreated` привязывает заказ к этой сделке (`findOpen` — только если договорённости нет). Если внесено больше, чем итог заказа, — в журнал заказа «переплата N ₸ по договорённости — нужен возврат», в событие `prepaidExcess`, подписчик ставит задачу ответственному.

**1.5. Заказ закрывает счета.** `OrdersService.place` с договорённостью в своей транзакции отменяет открытые `DealInvoice` этой сделки (тот же модуль, без порта); их счета Kaspi на номер отменяются после коммита.

**1.6. Онлайн-платёж — без чека, идемпотентно по операции.** `crm_payments`: `method text not null default 'manual'` (manual | kaspi | cloudpayments), `external_ref text`, `invoice_id uuid` (номер счёта для показа), уникальный индекс `(method, external_ref) where external_ref is not null`. `PaymentIntakeService.acceptOnline({deal, amount, paidAt, method, externalRef, invoiceId, note})`: под блокировкой сделки (B6); повтор той же операции возвращает уже записанный платёж; без эффектов (заметки, письма — в подписчиках после коммита). `DealPayments.add` принимает `createdById: string | null`. Правило B4 (ручной платёж — только с чеком) не меняется.

**1.7. Подтверждение оплаты** `DealInvoicesService.confirmPayment({invoiceId, method, externalRef, amount, paidAt})` в транзакции. Ключ идемпотентности — операция `(method, externalRef)`, а не статус счёта:
- счёт ждёт оплаты, сумма совпадает, у сделки нет заказа → `acceptOnline`, счёт `paid`, событие `ordering.deal_invoice_paid`;
- та же операция повторно → ничего;
- другая операция по уже оплаченному, отменённому или истёкшему счёту, у сделки нет заказа → деньги записываются (`acceptOnline`), счёт не меняется (или становится `paid`, если был не оплачен), событие `ordering.deal_invoice_overpaid` → заметка и задача «повторная оплата — нужен возврат»; доступ повторно не выдаётся;
- у сделки уже есть заказ или сделки нет → в sales деньги не пишутся (их нельзя ни вернуть, ни зачесть); событие `ordering.deal_invoice_orphan_payment` → заметка в сделке (если есть), задача и уведомление «оплата пришла по закрытому счёту — нужен возврат или зачёт в заказ»; внутри `settle` не бросать — иначе вечная повторная обработка.
- Сумма Kaspi/CloudPayments не совпала со счётом → как сейчас у Kaspi (`AmountMismatch`, failed), плюс задача менеджеру.

**1.8. Порядок блокировок** один для всех путей: `deal_invoices` → `payment_invoices` → `crm_deals`. Kaspi `settle` для счёта сделки сначала блокирует `deal_invoices` (по `target.id`), потом свою попытку. Ручное подтверждение блокирует счёт до `DealPayments.add`. Сетевые запросы к Kaspi — никогда под этими блокировками.

**1.9. Один открытый счёт на сделку:** частичный уникальный индекс `deal_invoices(deal_id) where status='pending_payment'`; выпуск — в транзакции под `pg_advisory_xact_lock` по сделке: отменить прежний открытый, вставить новый. Счёт Kaspi на номер и сообщение в чат — после коммита. Срок счёта — 7 дней.

**1.10. Сделку нельзя потерять с деньгами.** `mergeInto` переносит `crm_payments`, `crm_receipts` и `deal_invoices` в целевую сделку (сейчас платежи слияемой сделки удаляются каскадом — это исправление и для ручных платежей). Удалить сделку с платежами или с неотменённым счётом нельзя (409 с понятным текстом). Перевод сделки в «проигранную» или «успешную» и отклонение заявки отменяют её открытые счета (событие продаж → подписчик ordering).

**1.11. Ручной перевод.** «Оплата пришла» в счёте открывает обычный приём платежа с чеком, предвыбранным счётом и суммой счёта (менять нельзя; частичная — «не по счёту»). `AcceptInput.invoiceId`: внутри `uow.run` до записи денег порт `invoices.markPaidManually({invoiceId, dealId, paymentId?})` в ordering блокирует счёт, проверяет `invoice.dealId === deal.id` и статус (иначе 409 `invoiceAlreadyPaid` / `invoiceNotFound`). Событие `deal_invoice_paid` с `method='manual'`: заметку и письмо подписчики пропускают (их уже сделал приём платежа). Общая форма приёма платежа при открытом счёте или онлайн-платеже за последние 72 ч предлагает «по счёту P12» или явное «это другая оплата».

**1.12. Онлайн-платежи в CRM.** В `PaymentsPanel` — «Kaspi · операция …» / «Карта · …» и номер счёта вместо чека, без «нет чека»; удалить нельзя (409 «онлайн-платёж не удаляется — оформите возврат»); выгрузка — «онлайн» в колонке чека. Платёж, после которого оплачено больше договорённости, — отметка «переплата».

## 2. Платёжные системы

**2.1. Kaspi.** `PaymentTarget` получает `{kind:'deal_invoice', id: dealInvoiceId}` (колонка текстовая — DDL не нужен; расширить `$type` и запросы `paymentInvoices`). `confirmTarget` и `owned` — исчерпывающие `switch` с `never`; неизвестная цель — ошибка, а не «как заказ». `KaspiPaymentsService.payDealInvoice(token, {method, phone})` для страницы оплаты и `pushDealInvoice(invoiceId, phone)` для CRM — поверх `issue()`, комментарий «MyBooks P<n>». `InvoiceOwner {dealInvoiceToken}`, параметр `?pay=` в маршрутах счёта Kaspi (без `apiUser`, без 401 — иначе `apiFetch` уводит плательщика на вход).

**2.2. Сверка Kaspi для счетов сделок** — весь срок счёта: третий проход (каждые 15 минут) по попыткам `target_kind='deal_invoice'` в статусах pending | expired | cancelled за 8 дней. Перед отменой или истечением попытки — `refresh()`; отменять локально только если Kaspi подтвердил, что не оплачено (иначе оставить в сверке).

**2.3. CloudPayments:** `InvoiceId = P<n>` (проверка `^P\d+$` до разбора номера заказа), `accountId = P<n>`, почта не передаётся. `check`: 0 — ждёт оплаты и сумма совпадает; 13 — оплачен, отменён, истёк или у сделки заказ; 12 — сумма. `pay` → `confirmPayment(method='cloudpayments', externalRef=TransactionId)`.

**2.4. Способ оплаты должен существовать.** Перед выпуском — доступные способы: Kaspi (`available()`), карта (`isOnlinePayment()`), перевод (реквизиты заданы). Пусто — выпуск запрещён: «Нет способа оплаты: подключите Kaspi или укажите реквизиты перевода в «Интеграциях»». Форма показывает доступные способы.

**2.5. Реквизиты перевода** — «Интеграции» → «Оплата переводом»: номер Kaspi получателя и имя получателя (плюс переменные окружения). Тексты перевода в заказе, сертификате и счёте берут их отсюда; не заданы — способ «перевод» не показывается нигде (сейчас клиенты видят заглушку).

## 3. Страница оплаты `/pay/[token]` (и `/kk/pay/...`)

Публичная, noindex, `/pay/` в закрытых для роботов. Токен — 32 случайных байта base64url, проверка регуляркой до запроса в базу. Показывает: сумму, назначение («Персональная книга: <тариф>, предоплата / остаток / полная оплата»), номер счёта, срок. Не показывает имя и контакты клиента; телефон для Kaspi — маскированный (`+7 701 ••• •• 67`), по умолчанию сервер подставляет номер из счёта. Способы — `PaymentOptions`: Kaspi (`{kind:'deal_invoice', token}`) с именем получателя Kaspi (`orgName` сессии) и комментарием «MyBooks P12»; карта; перевод с «Я оплатил(а)» (лимит частоты, уведомление ответственному, заметка). Оплачен — «Оплата получена» и «доступ в кабинет отправили в WhatsApp» только при `access_status` sent/delivered, иначе «менеджер свяжется с вами»; кнопка входа. Отменён, истёк, по сделке заказ — понятный текст и контакты. Тексты — словарь `pay` ru/kk.

## 4. Доступ в кабинет после оплаты

**4.1. Аккаунт определяет identity, а не `deal.clientId`.** Подтверждённый телефон — только номер WhatsApp-чата счёта (GOWA или Wazzup, `chatId` похож на номер). Совпадение: `role='user'`, основной `users.phone` (нормализованный) равен номеру чата, ровно один аккаунт.
- Нет совпадения и нет `deal.clientId` → создать аккаунт `ensureClientAccount` (без события регистрации; логин — служебная почта телефона; имя — из чата или телефон; язык — из счёта; адреса ADMIN_EMAILS и `role != user` никогда), привязать.
- Совпадение есть → этот аккаунт (пароль не трогать).
- `deal.clientId` указывает на другой аккаунт, совпадение только по доп. телефону или заказам, чат не WhatsApp, номера нет → никого не привязывать и логин не раскрывать: клиенту нейтральное «Оплата получена, менеджер пришлёт доступ», менеджеру задача «Подтвердите, чей это аккаунт» с кандидатами и кнопкой «Отправить ссылку для входа».

**4.2. Что отправляется.**
- Аккаунт создан этим потоком или ни разу не использован (`lastSeenAt` пуст, нет книг и заказов) → ссылка «задайте пароль и войдите» + логин.
- Аккаунтом пользуются → «Оплата получена. Войдите как обычно: <логин> — <ссылка на вход>», без ссылки сброса (переназначенные номера). Есть настоящая почта — ссылка на неё, в чат «ссылку отправили на al•••@gmail.com».
- Доступ выдаётся один раз на клиента и сделку; следующие оплаченные счета — короткое «Оплата получена».

**4.3. Ссылка доступа.** `AuthService.issueAccessLink(userId, ttlMs ≤ 72 ч)`: строка `password_resets` с `purpose='access'` (новая колонка, по умолчанию `reset`), прежние неиспользованные ссылки клиента гасятся (`revokeUnused`). Погашение — отдельный путь `redeemAccessLink` (без выдачи прав администратора — их даёт только сброс по почте), при POST на `/reset/[token]` (предпросмотр WhatsApp ссылку не тратит), с текстом «Задайте пароль» для `purpose='access'`. Недействительная ссылка — «Напишите нам в WhatsApp» (ссылка wa.me), а не «Запросите новую» (у клиентов по телефону нет почты).

**4.4. Ссылка не хранится открытым текстом.** Сообщение уходит клиенту целиком, а в `crm_messages.text`, превью диалога и истории помощника — с маской `/reset/••••` (функция `redactSecrets` в домене переписки на всех путях записи: исходящее, эхо, входящее, захват эха — эхо сравнивается по замаскированному тексту). Во внутренние заметки и задачи ссылка не попадает — только «ссылка отправлена» и кнопка «Отправить заново».

**4.5. Выдача — шаг планировщика, с состоянием на счёте:** `access_status` (due | sent | delivered | failed | needs_manager | skipped), `access_user_id`, `access_message_id`, `access_attempted_at`. Подписчик `deal_invoice_paid` только ставит `due`. Проход планировщика (минутный) захватывает счёт (`access_status='due'` → в работе, с таймаутом захвата) и выдаёт доступ. Ошибка отправки (синхронная или позже статус доставки «error») → `failed`: одна внутренняя заметка в чате и одна задача, без новых токенов; автоматически повторить один раз при следующем входящем сообщении клиента в этом чате (окно Wazzup снова открыто). «Отправить доступ ещё раз» — в блоке счёта и в карточке клиента (`clients.create`, журнал).

**4.6. После оплаты (отдельные подписчики, каждый идемпотентен):** заметка в сделке «Оплачен счёт P12 — 15 000 ₸ (Kaspi, операция …)»; уведомление — ответственному, иначе выставившему счёт, иначе всем с `deals.edit`; письмо об оплате — только онлайн-оплаты; выдача доступа — `due`. Ручной путь заметку и письмо пропускает.

## 5. CRM

**5.1. Выставить** — кнопка «Счёт» в поле ввода чата (`ChatPanel`, режим клиента; в чатах и на странице сделки). Права: `chats.send` + `deals.edit`, сделка видна сотруднику (`assertVisible` по ответственному сделки, а не только диалога). Диалог без сделки — сделка создаётся как «Создать сделку» из чата. По сделке есть заказ — счёт нельзя (ссылка на оплату заказа). Форма: тариф и цена договорённости (подставлены из сделки), сумма (по умолчанию остаток = договорённость − оплачено; «Предоплата 50%», «Остаток», «Своя сумма» 1…остаток), язык ru/kk (по умолчанию язык аккаунта клиента, иначе ru), счёт Kaspi на номер клиента (если Kaspi доступен и номер чата — KZ мобильный; номер подставляет сервер), доступные способы, предпросмотр текста. Ключ идемпотентности формы — повторное нажатие не выпускает второй счёт. Лимит частоты на сотрудника.

**5.2. Сообщение клиенту** (на языке счёта): «Счёт P12 на оплату: персональная книга (<тариф>), <назначение> — 15 000 ₸. Оплатить: <ссылка> (Kaspi, картой или переводом). Действует до 23 октября.» + при счёте Kaspi на номер: «Счёт также пришёл в приложение Kaspi на номер +7 701 ••• •• 67 — получатель <orgName>». Не отправилось (`msg.status === 'error'`) — счёт остаётся, менеджеру ссылка для копирования.

**5.3. Блок «Счета»** в `PaymentsPanel` сделки и во всплывающем окне чата: номер, сумма, статус, способ, «клиент сообщил об оплате», статус доступа; «Скопировать ссылку», «Отправить ещё раз», «Отменить», «Оплата пришла», «Отправить доступ ещё раз».

**5.4. Срок счёта** — проход планировщика: просроченные → «истёк», счёт Kaspi на номер отменяется (после `refresh`), задача «Счёт P12 истёк неоплаченным — свяжитесь с клиентом».

## 6. Голосовые и вложения WhatsApp

Вложение открывается по id сообщения CRM: `/api/admin/chats/messages/[id]/media` — `chats.view` и видимость диалога (`assertVisible` по ответственному), путь шлюза только на сервере. Есть сохранённый путь — отдать; нет (история) и канал GOWA — `GET /message/:id/download?phone=…` (id и телефон проверены регулярками, кодируются), путь из ответа проверяется по сегментам (`^[\w-][\w.-]*$`, без `.` и `..`) и сохраняется в сообщении — второй раз не качается. Голосовые отдаются как `audio/ogg`; под плеером «скачать», если браузер ogg/opus не играет. `ChatPanel` для сообщений-вложений без файла показывает плеер/картинку по этому адресу.
