# Скорость MyBooks: замеры (P7, ADR 0009)

> Оптимизировать — только по цифрам из этого файла. Обновляйте таблицы датой замера, старые не стирайте.

## Как мерить

**Внешне (публичные страницы, без входа):**

```sh
for u in / /kk /login /kniga/mame /gift /api/health; do printf "%-14s" "$u"; for i in 1 2 3 4 5; do curl -s -o /dev/null -w "%{time_starttransfer} " -H "Accept-Encoding: br, gzip" "https://mybooks.kz$u"; done; echo; done
```

`/api/health` почти не работает на сервере, поэтому его время — это сеть и TLS. Вычтите его из времени страницы —
получится время сервера.

**Внутри (все маршруты, включая админку и API):** nginx пишет время каждого запроса к mybooks.kz в
`/var/log/nginx/mybook-timing.log` (формат `mybook_timing` в `/etc/nginx/conf.d/mybook-timing.conf`, без query string;
включено 2026-11-05, ротация — общая для `/var/log/nginx/*.log`).

```sh
ssh <сервер> 'sudo cat /var/log/nginx/mybook-timing.log' | node scripts/perf/route-latency.mjs --min 5 --top 40
```

Скрипт сводит идентификаторы в путях к `:id`/`:token`/`:n` и печатает p50/p95/p99/max и число 5xx по маршрутам.

## Выводы P7

1. **Узкого места в рантайме нет.** Публичные страницы — ~12 мс сервера в среднем, страницы редактора и CRM в реальном
   трафике — p95 ≤ 65 мс. Ни Go, ни Bun/Deno, ни вынос сервисов скорость для пользователя не поднимут — это
   подтверждает ADR 0009 цифрами.
2. **Единственное заметное замедление — окно выкатки:** запросы в секунды переключения отвечали ~0,5 с (см. находки).
   Это цена перезапуска процесса, а не кода; с ускоренным CI выкатки короче, но окно остаётся.
3. **Что делать дальше:** ничего не оптимизировать, пока лог таймингов не покажет маршрут с p95 > 300 мс вне окна
   выкатки. Повторный замер — той же командой из раздела «Как мерить» (лог пишется постоянно, ротация общая).

## Находки

- **2026-11-05 — окно выкатки.** В 06:03:57 (переключение релиза `e3bc77ef`) шесть запросов редактора ответили за
  470–537 мс при обычных 10–65 мс: основной процесс перезапускался, отвечала запасная копия на 3041. Если станет
  заметно — прогрев новой версии перед переключением (как прогрев обложек в `deploy.sh`) или PM2 cluster с reload.

- **2026-11-05 — двойной адрес upstream.** `upstream mybook_app { server localhost:3040 }` раскрывается в 127.0.0.1 и
  ::1, а Next слушает только `[::1]:3040`. Часть запросов сначала получает мгновенный отказ (в логе таймингов —
  `"0.000, 0.032"`), затем идёт на ::1; в `/var/log/nginx/error.log` — «connect() failed (111)». На время ответа почти
  не влияет (0 мс), но шумит в журнале ошибок. Чинить вместе с `HOSTNAME` в `deploy/ecosystem.config.cjs` (Next
  сверяет адрес с localhost для rewrite `/kk`) — отдельной задачей, с проверкой `/kk` за https.

- **2026-11-05 — память `mybook` 1,2–1,6 ГБ без трафика.** Не страницы (обход 114 адресов — ~320 МБ), а прогрев
  фото-обложек после выкатки: sharp/libvips оставлял процессу ~0,8 ГБ нативной памяти, плюс ~0,4 ГБ — поток PDF.
  Решение и замеры — [ADR 0010](adr/0010-jemalloc-and-sharp-cache.md): кэш libvips выключен, jemalloc; поток PDF
  закрывается после 10 мин простоя.
