## Как мерить

**Внешне (публичные страницы, без входа):**

```sh
for u in / /kk /login /kniga/mame /gift /api/health; do printf "%-14s" "$u"; for i in 1 2 3 4 5; do curl -s -o /dev/null -w "%{time_starttransfer} " -H "Accept-Encoding: br, gzip" "https://mybooks.kz$u"; done; echo; done
```

`/api/health` почти не работает на сервере, поэтому его время — это сеть и TLS. Вычтите его из времени страницы —
получится время сервера.

**Внутри (все маршруты, включая админку и API):** nginx пишет время каждого запроса к mybooks.kz в
`/var/log/nginx/mybook-timing.log` (формат `mybook_timing` в `/etc/nginx/conf.d/mybook-timing.conf`, без query string;
включено 2026-11-05, ротация — общая для `/var/log/nginx/*.log`).

```sh
ssh <сервер> 'sudo cat /var/log/nginx/mybook-timing.log' | node scripts/perf/route-latency.mjs --min 5 --top 40
```

Скрипт сводит идентификаторы в путях к `:id`/`:token`/`:n` и печатает p50/p95/p99/max и число 5xx по маршрутам.

## Выводы P7

1. **Узкого места в рантайме нет.** Публичные страницы — ~12 мс сервера в среднем, страницы редактора и CRM в реальном
   трафике — p95 ≤ 65 мс. Ни Go, ни Bun/Deno, ни вынос сервисов скорость для пользователя не поднимут — это
   подтверждает ADR 0009 цифрами.
2. **Единственное заметное замедление — окно выкатки:** запросы в секунды переключения отвечали ~0,5 с (см. находки).
   Это цена перезапуска процесса, а не кода; с ускоренным CI выкатки короче, но окно остаётся.
3. **Что делать дальше:** ничего не оптимизировать, пока лог таймингов не покажет маршрут с p95 > 300 мс вне окна
   выкатки. Повторный замер — той же командой из раздела «Как мерить» (лог пишется постоянно, ротация общая).

- **2026-11-05 — окно выкатки.** В 06:03:57 (переключение релиза `e3bc77ef`) шесть запросов редактора ответили за

- **2026-11-05 — двойной адрес upstream.** `upstream mybook_app { server localhost:3040 }` раскрывается в 127.0.0.1 и
  ::1, а Next слушает только `[::1]:3040`. Часть запросов сначала получает мгновенный отказ (в логе таймингов —
  `"0.000, 0.032"`), затем идёт на ::1; в `/var/log/nginx/error.log` — «connect() failed (111)». На время ответа почти
  не влияет (0 мс), но шумит в журнале ошибок. Чинить вместе с `HOSTNAME` в `deploy/ecosystem.config.cjs` (Next
  сверяет адрес с localhost для rewrite `/kk`) — отдельной задачей, с проверкой `/kk` за https.

- **2026-11-05 — память `mybook` 1,2–1,6 ГБ без трафика.** Не страницы (обход 114 адресов — ~320 МБ), а прогрев

### G2. Что держало память сайта и что сделано

Разбор пробным экземпляром того же релиза (`scripts/perf/probe/`: копия релиза на 127.0.0.1:304x без фона и миграций,
замер памяти каждые 5 с, обход всех 247 маршрутов `crawl.mjs`, задержка `lat2.mjs`, снимок кучи по SIGUSR2):

- Куча сайта сразу после старта — **~200 МБ, из них 164 МБ — строки**: исходники серверных чанков. Next при старте
  грузит все маршруты (`preloadEntriesOnStart`), а Turbopack кладёт общий серверный код (container и все модули) в
  отдельную копию чанка для каждой группы маршрутов: **120 МБ JS, уникальных модулей — 27 МБ, 24 копии чанка по 2,5 МБ**,
  отличающиеся только строкой `//# sourceMappingURL`. С кириллицей V8 хранит исходник по 2 байта на символ.
- Тяжёлых пакетов только для воркера/вёрстки в сайте нет: `@react-pdf` сайт не грузит (вёрстка — дочерний процесс),
  sharp/pg — внешние. Остальное (i18n, тексты, словари) — по 0,2–0,7 МБ, ленивые импорты дали бы единицы МБ.
- **Сделано:** `scripts/dedupe-server-chunks.mjs` после `next build` заменяет копии символьными ссылками на одну
  (рантайм Turbopack грузит чанк через `require`, а он кэширует по реальному пути — файл компилируется один раз).
  94 копии, −79 МБ файлов (`.next/server` 222 → 144 МБ). Откат — `MYBOOK_DEDUPE_CHUNKS=off` при сборке.
- Файлы хранилища — потоком с Range (`storage.openStoredFile`), без чтения целиком в память и без скачивания на диск.

### G3. Пилот Go `mybook-files`

`services/files` (Go, только stdlib, 7–13 МБ RSS): файлы хранилища по подписанной ссылке сайта. Режимы и откат —
[06-operations.md §2.5](06-operations.md). **Сверка** `scripts/files/parity.ts` на проде: 186 файлов бакета (298 МБ:
фото, PDF заказов, свои видео и кадры, вложения обращений) × 7 видов запроса (целиком, Range начало/середина/хвост/за
концом, два диапазона, If-None-Match) напрямую и через переписывание Next — **2604 сравнения, 0 расхождений** по статусу,
sha256 тела и заголовкам. Найдено и исправлено по пути: у 304 сайт отдавал `Content-Type`, а net/http Go — нет (RFC 9110):
сайт теперь тоже нет; у ответов без тела длину ставит сервер HTTP, у `text/*` через Next — сжатие (тело то же).

**Нагрузка файлами** — пробные экземпляры одного релиза, `/api/v/<токен>` (12 настоящих видео), 240 запросов по 8
параллельно (половина — Range, как плеер), 812 МБ; три прогона в разном порядке:

| Путь | TTFB p50 / p95, мс | CPU сайта, с | CPU Go, с | пик RSS сайта, МБ |
|---|---:|---:|---:|---:|
| до G2 (копия на диске после первого скачивания; без склейки чанков) | 15–17 / 32–53 | 1,9–2,5 | — | 405–427 |
| G2: сайт сам из S3 потоком (`off`) | 12–17 / 45–60 | 5,4–7,4 | — | 307–392 |
| **`proxy`: сайт → Go** | **9,5–11 / 24–29** | 3,5–5,5 | 1,8–1,9 | **271–277** |
| `redirect`: 302 → Next (переписывание) → Go | 10–13 / 29–45 | 5,4–5,9 | 2,0 | 258–268 |

Изолированно TTFB из S3 одинаков (Node 4,2 мс, Go 3,2 мс p50): выигрыш Go в сверке и под нагрузкой — тёплые TLS-соединения
к бакету (net/http держит их 90 с, fetch Node — несколько секунд) и меньше работы сайта на байт (локальный HTTP вместо
TLS + web-потоков). Общий CPU (сайт + Go) — примерно как у G2. «До G2» быстрее по пропускной способности только потому,
что отдавал с локального диска уже скачанные копии (первое открытие ждёт полного скачивания, диск растёт).

**Гейт G3** (паритет 100 %, TTFB ≤ текущего, RSS сайта под нагрузкой файлами не растёт) — **пройден в режиме `proxy`**:
включено 24.11 ~04:15 (`echo proxy > ~/mybook-flags/files-service`). Байты в `proxy` ещё идут через сайт (передача
потока); совсем мимо Node — режим `redirect` после строки nginx ([06-operations.md §2.5](06-operations.md), нужен sudo
владельца). Без nginx `redirect` не лучше `proxy` (переписывание Next тратит столько же CPU) — не включаем.

Проверка на проде после включения (журнал, 23:39 UTC): сайт — `route:answer-file` 8 запросов (200 ×4, 206 ×4), 6,7 МБ;
`mybook-files` — `go:s3` те же 8 запросов и 6,7 МБ. Счётчики маршрутов сайта пишутся с `2a0d9275` (до него маршруты Next

Что дало больше: исходник бандла (15,6 МБ) V8 держал двухбайтной строкой — из-за русских комментариев, которые esbuild
оставляет, и не-ASCII в регулярных выражениях и `sql\`…\`` (esbuild их не экранирует). Сборка теперь

0 различий (у 21 шаблона `sql` меняется только `.raw`, drizzle берёт «готовые» строки). То же для `pdf-worker.mjs`
(4,3 МБ, ASCII). Откат — `MYBOOK_WORKER_MINIFY=off`, `MYBOOK_ASCII_BUNDLE=off` при сборке.
