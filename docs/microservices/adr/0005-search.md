# ADR 0005. Поиск: Postgres сейчас, Meilisearch позже, Elasticsearch — нет

**Статус:** предложено · **Дата:** 2026-11-05

## Контекст

CRM ищет по клиентам, сделкам, заказам, задачам, звонкам, чатам и книгам. Сейчас
`src/modules/reporting/infrastructure/Search.ts` делает `ILIKE`/`JOIN` по нескольким таблицам.
Объём — сотни тысяч строк, не миллионы.

## Решение

| Этап | Решение |
|---|---|
| Сейчас и до волны 5 | PostgreSQL: `pg_trgm` + FTS (`tsvector`), составные индексы, `unaccent` при необходимости |
| Если нужен поиск с опечатками/релевантностью | Meilisearch, индексы из событий, отдельный сервис/контейнер |
| Если нужен поиск по логам/аналитика на десятки миллионов документов | OpenSearch — только отдельный ADR с бюджетом RAM |
| Elasticsearch | Не используем |

## Почему не Elasticsearch

- Минимум 1–2 ГБ RAM только под JVM/кластер; на сервере 8 ГБ с PDF до 1.5 ГБ это критично.
- Нужен отдельный сервис, мониторинг, бэкапы, обновления.
- Для 54 таблиц и сотен тысяч строк Postgres FTS/trigram даёт приемлемую скорость.
- Elasticsearch и OpenSearch функционально дублируются; если понадобится — OpenSearch (лицензия,
  совместимость).

## Порог для Meilisearch

- жалобы на качество поиска (опечатки, порядок);
- p95 `reporting.search` > 300 мс;
- потребность в фасетах/подсветке, которых нет в Postgres.

Индекс: `clients`, `deals`, `orders`, `books`, `messages` (последние — с ограничением по правам).
Обновление — из событий (`*.created`, `*.updated`), полная переиндексация — по расписанию.

## Последствия

- На волнах 1–5 не добавляем новый сервис поиска; оптимизируем индексы и запросы.
- `reporting` остаётся в `core`; при выносе в `insights` поиск переезжает вместе с ним.
- Если появится Meilisearch — это ещё один контейнер (~100–200 МБ) и синхронизация; решение
  принимается по метрикам, а не заранее.
