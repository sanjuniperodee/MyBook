# ADR 0002. Вынос бэкенда: отдельное Next-приложение + remote `container()`

**Статус:** предложено · **Дата:** 2026-11-05

## Контекст

Нужно убрать БД и бизнес-логику из веб-приложения, не меняя UI и не переписывая 138 API-роутов и
38 файлов server actions.

В коде есть удобный шов: `container()` — корень композиции. Через него страницы, actions и роуты
получают модули. Вызовов — 643 в 202 файлах.

Альтернативы:

1. Переписать все роуты на Fastify и все страницы на HTTP-клиент — большой объём, высокий риск
   регрессий, много месяцев до первого результата.
2. Оставить всё как есть и «ходить в БД из web» — это не вынос бэкенда.
3. Вынести весь бэкенд в отдельное приложение, сохранив `container()` как интерфейс, и подменить
   транспорт.

## Решение

**Волна 1:**

- `apps/api` — отдельное Next.js-приложение без страниц: `app/api/**`, `instrumentation`, модули,
  `shared`, `server`, `drizzle`. Оно обслуживает все существующие роуты **без переписывания**.
- `apps/web` — страницы, компоненты, server actions, BFF. Не импортирует `pg`, `drizzle`, модули,
  `shared/infrastructure`.
- `container()` в web сохраняет тип, но возвращает **remote proxy**: путь метода → `POST
  /internal/v1/rpc` → вызов реального контейнера в api.
- Публичные URL не меняются: nginx/rewrite отправляет `/api/**` в api; server actions остаются в web
  и ходят в api по internal HTTP.
- Флаги `BACKEND_MODE=inprocess|shadow|strict|http`; parity-режим сравнивает ответы.

**Почему Next, а не сразу Fastify:**

- 138 роутов уже написаны под `NextRequest`/`NextResponse`, `cookies()`, `headers()`, стриминг, SSE.
  Переписывание на Fastify — отдельный крупный проект, который не даёт пользователю ничего на
  волне 1.
- Два Next-приложения собираются из одного кода; риск минимален.
- Новые сервисы (publishing, conversations, platform, ai) пишутся на Fastify сразу. `core` можно
  перевести на Fastify позже или разнести на commerce/crm.

## Последствия

- Два процесса, два билда, больше памяти (~1.2–1.6 ГБ на web+api вместо ~0.5–0.7 ГБ).
- RPC — распределённый монолит. Это **временный шов**, не целевой контракт. Публичные API остаются
  REST/OpenAPI; RPC удаляется по мере появления явных endpoint'ов.
- Нужны: internal auth (HMAC), allowlist методов, superjson, обработка ошибок, таймауты, запрет
  транзакций через RPC.
- Плюс: UI не трогаем; 643 вызова не переписываем; откат — флагом.

## Ограничения

- Методы, возвращающие агрегаты/классы с поведением, маппятся в DTO на стороне api.
- `Buffer`/`ReadableStream` — только через отдельные роуты, не через RPC.
- Размер ответа > 2 МБ — отдельный роут.
- Один RPC-вызов не должен открывать транзакцию, охватывающую несколько модулей.
