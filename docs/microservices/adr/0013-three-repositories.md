# ADR 0013. Три репозитория: бэкенд, веб, мобильное приложение

Статус: принято 26.11.2026 (решение владельца). Меняет раскладку из `08-monorepo.md`: монорепо остаётся только у
бэкенда.

## Контекст

После A5 (ADR 0012) веб ходит только в API v1: оба allowlist храповика пусты. Мобильное приложение (Flutter, `mobile/`)
с самого начала работает только через API v1. Владелец хочет выкатывать и вести их отдельно: веб, возможно, на Vercel
(`vercel-trial.md`), приложение — своим циклом выпусков.

## Решение

| Репозиторий | Что в нём | Выкатка |
|---|---|---|
| `MyBook` (этот, история сохраняется) — **бэкенд** | `apps/api`, `src/modules`, `src/server`, воркеры, PDF, Go-сервисы, миграции `drizzle`, `deploy/`, вебхуки, `packages/contracts` (источник правды API v1) | как сейчас: push в master → CI → 185.102.75.191 |
| `mybook-web` — **веб** | Next: сайт, кабинет, редактор, CRM `/admin`, i18n, `public/`; к данным — только `@mybook/contracts` + API v1 | свой CI: наш сервер (PM2 `mybook`) или Vercel — по итогам замера |
| `mybook-mobile` — **приложение** | `mobile/` целиком (CRM и клиентское «MyBooks», flavors) | свой CI: APK/iOS → `/admin/app`, магазины |

- Репозитории приватные, история переносится `git filter-repo` по путям.
- **Контракты.** Источник — бэкенд. `@mybook/contracts` (и чистый общий код `src/shared/domain`, если вебу он нужен)
  публикуется в GitHub Packages с версией. Веб зависит от версии. Dart-клиент `mybook_api.g.dart` генерирует бэкенд,
  в мобильный репозиторий он попадает пулл-реквестом из CI бэкенда (нужен токен с доступом к `mybook-mobile`, его
  заводит владелец). До появления токена генератор `scripts/contracts/generate.ts` запускают вручную с путём к checkout приложения (параметр пути добавляется в шаге 1).
- **Совместимость API.** Пока веб и приложение выкатываются отдельно, API v1 меняется только добавлением. Удалить поле
  или маршрут можно, когда его не использует ни одна выпущенная версия.

## Порядок

1. **Мобильное приложение** — сразу: оно не зависит от кода веба. Бэкенд оставляет генератор Dart-клиента и проверку
   его свежести у себя.
2. **Конец A5.** Все разделы во `WEB_USE_API_V1`, `PARITY_MODE=off`. Затем из веба убираются локальные ветки
   (`local:` в `v1WebRead`/`v1WebAction`, `v1-local-bridge-*`): веб не содержит кода бэкенда даже транзитивно. Это
   проверяет тест: сборка веба без `DATABASE_URL` и без `src/modules`/`src/server` бэкенда.
3. **Вынос веба** в `mybook-web` со своей выкаткой. Пока она не заработала на проде, монорепо выкатывает всё как раньше.
   Это точка отката.
4. **Бэкенд удаляет код веба** только после того, как прод неделю работает от `mybook-web`.

## Последствия

- Изменение контракта — два шага: релиз бэкенда с новой версией пакета, затем веб и приложение.
- Сквозные тесты «веб + API» уходят в CI веба против API стенда или прода (только чтение).
- Правило «веб и приложение пиксель в пиксель» (общие числа и подписи) сохраняется: общий модуль — в пакете, а не копия.
