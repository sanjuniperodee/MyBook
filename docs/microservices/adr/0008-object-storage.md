# ADR 0008. Объектное хранилище: Yandex Object Storage (S3 API)

**Статус:** принято пользователем · **Дата:** 2026-11-05

## Контекст

Фото книг, PDF, превью и вложения сейчас лежат на локальном томе `storage/` рядом с приложением.
После выноса publishing и рендера в отдельный сервис общий диск превращается в скрытую связь:
несколько процессов должны видеть одни и те же файлы, а при переезде на несколько машин том
перестаёт работать.

Варианты:

1. Оставить локальный том — просто сейчас, плохо для сервисов и бэкапов.
2. MinIO на том же VPS — S3 API, но +200–300 МБ RAM и ещё один процесс на 8 ГБ.
3. Внешний S3-совместимый сервис — не занимает RAM, даёт versioning/lifecycle.
4. Своё файловое хранилище с HTTP — писать и поддерживать самим.

Пользователь создал бакет в **Yandex Object Storage** и передал доступы для настройки.

## Решение

- Провайдер: **Yandex Object Storage**, S3 API.
- Endpoint: `https://storage.yandexcloud.net`, region `ru-central1`, bucket `mybooks`.
- Доступ: профиль AWS CLI `yc-storage`; для приложения — переменные `S3_*` в `.env.local`.
- Ключи **не коммитятся**. В docs — только имена переменных и инструкции.
- Бакет приватный; отдача — подписанные URL или серверный поток.
- Для локальной разработки/тестов допускается MinIO в compose (тот же S3 API); прод — Yandex.

## Последствия

- Минус ~200–300 МБ RAM на хосте (MinIO не нужен).
- Появляется сетевая зависимость: таймауты/retry, кэш, деградация при недоступности S3.
- Нужны versioning, lifecycle, бэкап и ротация ключей.
- Миграция `storage/` — копирование с сохранением ключей, затем переключение чтения.
- Локальные тесты без сети — MinIO; интеграционные тесты S3 — отдельный профиль.

## Почему не MinIO в проде

- 8 ГБ уже делят веб, PDF, Postgres и чужие сайты; лишние 200–300 МБ и процесс не бесплатны.
- Внешний S3 даёт versioning/lifecycle/бэкап без обслуживания диска.
- MinIO остаётся для локального стенда, где внешний бакет не нужен.

## Почему не локальный том

- Несколько сервисов на одном хосте ещё могут делить том, но это скрытая связь и единая точка отказа.
- При переезде publishing на вторую машину том не поедет.
- Бэкап и права доступа к файлам сложнее, чем у S3.

## Безопасность

- Ключи, переданные в чате, считаются известными; при публикации/шаринге чата их нужно перевыпустить.
- В репозитории ключей нет; `.env.local` и `~/.aws/credentials` — `chmod 600`.
- Публичных ACL нет; подписанные URL — короткий TTL.
- Фото/письма — персональные данные; доступ только владельцу/сотруднику с правом.

## Открытые вопросы

- CDN перед бакетом — после метрик волны 2.
- Второй бакет/регион для бэкапа — до волны 2.
- Ротация ключей — до продакшена publishing.
