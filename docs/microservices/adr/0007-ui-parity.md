# ADR 0007. Совместимость UI: визуальный контракт, golden DTO и shadow-режим

**Статус:** предложено · **Дата:** 2026-11-05

## Контекст

Требование пользователя: «текущий фронт визуально вообще не поменялся для юзера админки и клиентской
части». При выносе бэкенда меняется источник данных, а значит есть риск:

- изменилась форма DTO (поле, тип, порядок, null/undefined);
- изменились тексты ошибок/пустых состояний;
- изменились заголовки кэша/редиректы;
- страница стала медленнее и «мигает»;
- админка/кабинет выглядят иначе на ru/kk или mobile.

Одних unit-тестов недостаточно: они не видят DOM/CSS и реальные данные.

## Решение

Четыре уровня проверки (все обязательны для волны 1):

1. **Скриншоты Playwright** ключевых маршрутов: админка и кабинет, ru/kk, desktop/mobile,
   фиксированные seed-данные, маски динамики. `toHaveScreenshot`, 0 diff.
2. **Golden DTO**: JSON-снимки ключевых read-моделей; сравнение формы и значений при переходе на
   HTTP.
3. **Parity shadow**: BFF зовёт in-process и HTTP, сравнивает нормализованные ответы, пишет
   расхождения; пользователь не страдает.
4. **Существующий визуальный стенд PDF/HTML** (`scripts/visual/check.sh`) — для publishing, чтобы
   книга не изменилась.

Плюс:
- флаги `BACKEND_MODE`/`*_MODE` для мгновенного отката;
- канарейка 1–5% или отдельный аккаунт;
- запрет менять `app/**`/`components/**` в PR переезда (кроме импорта типа/адаптера данных);
- отдельный PR на любое согласованное изменение вида.

## Что считается изменением вида

- Любой diff пикселей на скриншотах (кроме замаскированных зон).
- Изменение DOM-структуры ключевых селекторов, CSS-классов, порядка элементов.
- Изменение текста, числа, формата даты/валюты, пустого состояния.
- Изменение URL, метода, статуса, заголовков кэша.
- Изменение поведения формы (валидация, автосохранение, редирект).

Всё это — не «рефакторинг», а продуктовое изменение; нужно согласование и запись в PROGRESS.

## Почему не только скриншоты

- Скриншоты не ловят API-контракт для Flutter и для клиентских fetch-вызовов.
- Не ловят разницу в данных, которая визуально не проявилась (например, `null` вместо `0`).
- Не ловят медленные регрессии (N+1), которые проявятся под нагрузкой.
- Поэтому DTO golden + parity + метрики обязательны.

## Последствия

- Нужен детерминированный seed и тестовая БД; это отдельная работа (M0.3).
- Эталоны скриншотов нужно хранить и обновлять осознанно; в CI — артефакт diff.
- Parity добавляет нагрузку в shadow-режиме; включать выборочно/на канарейке.
- Зато переключение волны 1 становится измеримым, а не «на глаз».
