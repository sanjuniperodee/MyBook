# ADR 0012. Разделение web / api / mobile: API v1 — единственный путь к данным

**Статус:** принято (решение владельца, 2026-11-24) · **Дата:** 2026-11-24
**Дополняет:** [0009](0009-modular-monolith-with-workers.md) (модульный монолит + процессы) и
[0011](0011-go-services-strangler.md) (Go по замеру). **Возвращает** волну 1 target A
([02](../02-target-architecture.md), [03](../03-migration-plan.md)) — в виде душителя, а не переноса кода.

## Контекст

Владелец: «фронт — отдельным сервисом, бэк — отдельно, мобилка — отдельно; мобильное приложение и фронт обращаются к
бэку по API; в мобильном приложении сразу сделать и клиентскую часть». Сейчас:

- веб (Next) сам ходит в БД через `container()`; мобильное приложение продажника — через `/api/mobile/*` (60 маршрутов,
  только CRM, форма ответов не описана нигде, кроме кода);
- клиентской части в приложении нет; чтобы её сделать, нужен стабильный описанный API: книги, ответы, фото, обложка,
  заказ, оплата;
- гейт G0 закрыт (baseline, визуал, golden/parity — M0.1–M0.7); target A владелец теперь подтвердил.

## Решение

1. **Контракт первым — `packages/contracts`.** Zod-схемы запросов и ответов по доменам, таблица маршрутов `v1`
   (метод, путь, кто может звать, схемы). Из неё: OpenAPI 3.1 (`/api/v1/openapi.json`), TS-клиент
   (`createApiClient`, типы без генерации) и Dart-клиент (`mobile/lib/api/mybook_api.g.dart`, свой генератор на
   `package:http`). Сгенерированные файлы в git; тест `tests/api-v1.test.ts` роняет CI при расхождении.
   Совместимость: менять ответ несовместимо нельзя — новое поле необязательное или новый маршрут.
2. **`apps/api` — процесс `mybook-api`** (PM2, 127.0.0.1:3060), собран из того же кода, что сайт
   (`scripts/build-api.mjs`, как mybook-worker). Без фреймворка: `node:http` + маршруты контракта — меньше памяти и
   слоёв; запрос → вход и права → разбор схемами контракта → тонкий обработчик над сервисами модулей → DTO.
   Обработчик не содержит правил домена: они в модулях (DDD — прикладной сервис и агрегаты), API — адаптер.
3. **Вход и права — тот же механизм, что у сайта (ADR 0006):** сессия из `sessions` по cookie `mb_session` (веб) или
   `Authorization: Bearer` (приложение); `apiUser`/`apiBook`/`apiStaff`, роли, «только свои» — те же функции.
   В процессе API `next/headers` даёт заголовки текущего запроса (AsyncLocalStorage), поэтому общий код не дублируется.
   Internal JWT из ADR 0006 не нужен, пока api и web — один код и одна БД; понадобится при разделении данных.
4. **Веб — душитель, без переноса кода.** Разделы веба по одному переходят на TS-клиент API за флагом, с parity-сверкой
   (`src/server/parity.ts`, golden DTO). Тест архитектуры с белым списком: в разделах, переведённых на API, нет `pg`,
   `drizzle`, `@/modules`; список исключений только сокращается. Первый шаг — общие схемы: маршрут сайта
   `PATCH /api/books/:id/questions/:qid` уже проверяет тело схемой контракта `QuestionPatch`.
5. **Маршрутизация:** nginx `location ^~ /api/v1/` → 127.0.0.1:3060 (мимо Next), запасной путь — переписывание в
   `next.config.ts`. Вебхуки (Kaspi, CloudPayments, GOWA, почта) переезжают в api отдельными шагами с теми же
   адресами (nginx), по одному, с проверкой подписи как сейчас.
6. **Мобильное приложение** получает и CRM, и клиентскую часть только через v1; `/api/mobile/*` остаётся, пока экраны
   не переведены, новые экраны — только на v1.

## Почему так, а не M1.1 из плана (перенос в apps/web + packages/core)

- Перенос 166 тыс. строк `git mv` и remote-proxy на 643 вызова — недели без рабочего результата; душитель даёт
  рабочую часть каждой выкаткой и откат флагом.
- Описанный контракт нужен мобильному приложению сейчас; remote-proxy `container()` контракта не даёт (RPC на
  внутренние методы — та же связность, только по сети).

## Цена и как держим скорость

- Память: второй процесс с кодом модулей — ~150 МБ (как mybook-worker после G4: 142–149 МБ пустой). Замер — perf.md.
- Лишний хоп для веба, когда раздел переведён: api на 127.0.0.1, keep-alive (65 с, дольше nginx), один JSON без
  двойной сериализации (обработчик отдаёт DTO, а не модель для повторной сборки); SSR веба зовёт api напрямую по
  127.0.0.1, мимо nginx.
- Приложению — ничего лишнего: nginx → api.

## Откат

- `MYBOOK_API=off` при выкатке — процесс не запускается; nginx-блок `/api/v1/` убрать (копия конфига до правки —
  06-operations §2.9). Веб от api пока не зависит; переведённый раздел — флаг раздела обратно в «in-process».

## Последствия

- Новый маршрут = схема в контракте + обработчик (тип `Handlers` не даст забыть) + перегенерация клиентов.
- Ошибки — в формате сайта `{ error, code }`: текст на языке пользователя, код стабильный.
- Ответ вне прода сверяется со схемой (несоответствие — 500 в тестах), в проде не сверяется (скорость).
