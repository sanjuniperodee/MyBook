# ADR 0009. Модульный монолит + отдельные процессы вместо микросервисов; TypeScript на Node

**Статус:** принято (владелец поручил взвесить и решить, 2026-11-05) · **Дата:** 2026-11-05
**Заменяет:** [0001](0001-target-topology.md) и [0002](0002-backend-extraction-strategy.md) как
ближайшую цель. Они остаются описанием target A на случай, если сработает триггер из §5.

## Контекст

Чего хочет владелец:

1. Быстрее собирать и выкатывать изменения.
2. Ограничить зону изменений: правка в одной области не должна задевать остальные, а разработка
   (в основном агентами) должна быть дешевле.
3. Не упереться в размер монолита: он растёт.
4. Возможно, переписать часть на более быстром языке (Go) или runtime (Bun/Deno).

Что показали замеры (GitHub Actions, `deploy.yml`, последние выкатки):

| Шаг | Время |
|---|---:|
| Типы (`tsc`) | 23–37 с |
| Линтер | 39–56 с |
| **Тесты (`vitest`)** | **224–351 с** |
| Сборка Next | 61–77 с |
| Выкатка на сервер | 80–91 с |
| **Итого** | **8–15 мин** (плюс ожидание в очереди `concurrency`) |

Сумма времени всех тестовых файлов — 290 с; половина приходится на четыре PDF-теста
(`pdf-opener-limits` 56 с, `pdf-critical` 45 с, `cover-back-color` 32 с, `pdf` 20 с). Все шаги идут
последовательно в одном job на 4-ядерном раннере.

Прочее:

- Код: 166 тыс. строк TS, 17 модулей с границами, которые держит `tests/architecture.test.ts`.
  Но 17 файлов вне модулей (`src/server/*`, `src/lib/book/*`) ходят в БД напрямую — граница размывается.
- Команда: владелец + агенты. Сервер общий (MyBooks, DoseWear, my-test, Daiyn, kaspi-pos, GOWA),
  ~3 ГБ занято без нагрузки, есть желание уменьшить до 4 ГБ.
- Замеров медленных страниц/API нет: на рантайм никто не жаловался с цифрами.

## Решение

### 1. Архитектура: модульный монолит + отдельные процессы

Один репозиторий, один язык, одна БД, один артефакт сборки. Тяжёлое и долгоживущее выносится
**в отдельные процессы PM2 из той же кодовой базы**, а не в сервисы с собственным API:

| Процесс | Что делает | Зачем |
|---|---|---|
| `mybook` (web) | страницы, API, server actions | как сейчас |
| `mybook-render` | PDF, превью, фото, ffmpeg | падение/пик памяти рендера не роняет сайт; свой `max_memory_restart` |
| `mybook-messaging` | вебхуки-ретраи, исходящие, IMAP, бот, АТС | внешние сбои и долгие соединения вне веб-процесса |
| `mybook-scheduler` | cron-задачи, outbox-диспетчер | один экземпляр, не зависит от числа web-процессов |

Связь — через то, что уже есть: `outbox_events` и очередь задач в Postgres (BullMQ/Redis — только
если Postgres-очереди не хватит, отдельным ADR). Процесс-воркер вызывает тот же `container()`;
сетевого RPC между web и бэкендом нет.

Это даёт ту изоляцию, ради которой планировались волны 2–3, без волны 1 (RPC-прокси на 643 вызова),
без второго Next-приложения (+600–900 МБ) и без распределённых транзакций.

### 2. Скорость выкатки — через CI, а не через сервисы

Сборка Next занимает минуту; микросервисы ускорили бы именно её. Узкое место — тесты и
последовательные шаги. Поэтому:

- типы, линтер, тесты и сборку запускать **параллельными job-ами**;
- тесты делить на шарды (`vitest --shard`), PDF-тесты — в отдельный шард;
- кэшировать `.next/cache` между прогонами;
- цель: **пуш → прод ≤ 4–5 мин** (сейчас 8–15).

### 3. Зона ответственности — через границы модулей

Ограниченная зона изменений и дешёвая разработка агентами достигаются строгими границами внутри
монолита, а не сетью:

- архитектурный тест распространить на `src/server` и `src/lib`: доступ к БД — только в модулях;
- новые фичи — только модулем (`src/modules/<context>`), а не файлом в `src/server`;
- карта модулей в docs: что модуль делает, его публичный фасад, его тесты. Агент берёт в контекст
  один модуль, а не весь проект;
- тесты по модулю: `vitest run tests/<module>*` для локальной проверки.

### 4. Язык и runtime: TypeScript на Node LTS

**Go — нет.**

- Авторизация — это чтение cookie и один запрос к сессии в БД (миллисекунды). Go не ускорит её
  заметно, а отдельный сервис добавит сетевой хоп — суммарно станет медленнее.
- Переписать вход, 2FA, сессии, права, IP-allowlist, сброс пароля — security-критичный код без
  выигрыша для пользователя.
- Второй язык = второй набор типов, тестов, сборки и деплоя; DTO придётся дублировать или
  генерировать. Для команды из владельца и агентов это удорожание, а не удешевление.
- Тяжёлое CPU уже не на JS: картинки — `sharp` (libvips, C). PDF — `@react-pdf/renderer`, он живёт
  только в JS.

**Bun / Deno — не переходим.**

- Next.js официально поддерживается на Node; на Bun/Deno — с оговорками. Риск для прода с
  платежами и WhatsApp выше пользы.
- Зависимости, которые надо было бы перепроверять: `sharp`, `@react-pdf/renderer`, `fontkit`,
  `hunspell-asm`, `imapflow`, `pg`, `web-push`.
- Выигрыш Bun — в скорости установки и запуска тестов, а не в скорости сайта. Те же минуты в CI
  дешевле получить параллелизмом (§2).

## 5. Когда пересмотреть (триггеры)

Выносить настоящий сервис (своя БД-схема, свой API, свой деплой) — только при одном из условий:

| Триггер | Что выносить |
|---|---|
| Над разными доменами параллельно работают 3+ человека и мешают друг другу релизами | этот домен (обычно CRM) |
| CI после §2 всё равно > 10 мин, и узкое место — сборка, а не тесты | web отдельно от бэкенда (target A, волна 1) |
| Один домен требует другого масштаба: 10× сообщений, отдельная машина под рендер | этот процесс → сервис на своём хосте |
| Замер показывает, что узкое место — CPU в Node на изолированном участке со стабильным контрактом | только этот участок, тогда — Go/Rust |

## Последствия

- Волна 1 (web/api + RPC) и target A отложены. Документы 02/03 остаются справкой.
- Волна 0 (визуальные эталоны, golden DTO, parity-утилиты, каркас workspaces) полезна и в монолите:
  её стоит влить в master.
- Новый план — [PROGRESS.md](../PROGRESS.md), раздел «Направление после ADR 0009».
- Память: пик PDF и так живёт на сервере (сейчас внутри `mybook`, лимит 4000M); добавляется только
  базовая память 2–3 процессов-воркеров (~150–300 МБ каждый), а не 5 сервисов и второй Next.
