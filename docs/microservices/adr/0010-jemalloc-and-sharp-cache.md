# ADR 0010. jemalloc для сайта и воркера; кэш libvips выключен

**Статус:** принято (владелец поручил разобрать память, 2026-11-05) · **Дата:** 2026-11-05

## Контекст

На сервере (8 ГБ, общий с другими сайтами) процесс `mybook` держал 1,2–1,6 ГБ почти без трафика. Разбор:

| Что | Память |
|---|---:|
| `mybook` сразу после старта | ~300 МБ |
| после обхода всех 114 публичных страниц (локально, копия базы) | ~320 МБ |
| после прогрева обложек при выкатке (`warm_covers` в `deploy.sh`, 50 обложек) | ~1050–1150 МБ |
| поток вёрстки PDF после работы (закрывается после простоя с `f118465e`) | +~0,4 ГБ |

Куча JavaScript при этом — ~200 МБ: остальное — нативная память `sharp`/libvips. Фото-обложки растрируются из SVG со
встроенным снимком до 2400 px; после работы память остаётся у процесса по двум причинам:

1. **Кэш операций libvips** (по умолчанию 50 МБ / 100 операций) держит расшифрованные снимки. Повторов одних и тех же
   операций у нас почти нет: готовые растры кэшируем сами (LRU обложек, уменьшенные снимки).
2. **malloc glibc** почти не возвращает системе освобождённое потоками libvips (фрагментация по аренам).

Замер на сервере (Ubuntu, glibc 2.39, Node 22, sharp 0.35; 40 снимков × миниатюра и крупное превью, как в
`/api/covers`; память процесса после простоя):

| Вариант | МБ |
|---|---:|
| как было (glibc, кэш libvips) | 595–610 |
| `MALLOC_ARENA_MAX=2` | 434–484 |
| кэш libvips выключен | 378 |
| jemalloc | 286–351 |
| jemalloc с фоновым возвратом (`background_thread`, `dirty_decay_ms:1000`) | 233 |
| jemalloc + кэш выключен | 157 |
| **jemalloc с фоновым возвратом + кэш выключен** | **83** |

## Решение

1. **Кэш libvips выключен** (`src/shared/infrastructure/sharpMemory.ts`) при старте сайта, `mybook-worker` и каждого
   потока PDF. У sharp две сборки (CommonJS и ES-модуль), каждая при загрузке включает кэш заново, поэтому функция
   загружает обе и только потом выключает.
2. **jemalloc** — `LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2` и
   `MALLOC_CONF=background_thread:true,dirty_decay_ms:1000,muzzy_decay_ms:0` для `mybook` и `mybook-worker`
   (`deploy/ecosystem.config.cjs`). Библиотека — пакет Ubuntu `libjemalloc2`, на сервере уже стоит. Её нет или
   `MYBOOK_JEMALLOC=off` — обычный malloc, как раньше. jemalloc для sharp на glibc советуют сами авторы sharp.

## Последствия

- Ожидаемо `mybook` в простое — ~0,3–0,5 ГБ вместо 1,2 ГБ; это приближает сервер 4 ГБ.
- Цена: фоновый поток jemalloc и чуть больше работы на возврат памяти; на скорость ответов не влияет заметно
  (проверить по логу таймингов, perf.md).
- Откат без выкатки: `MYBOOK_JEMALLOC=off pm2 start deploy/ecosystem.config.cjs` (после `pm2 delete mybook mybook-worker`).
- CI и локальная разработка не меняются: на macOS и в тестах jemalloc не подключается.
