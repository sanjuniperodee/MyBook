# ADR 0006. Аутентификация: свои сессии + internal JWT, без Keycloak

**Статус:** предложено · **Дата:** 2026-11-05

## Контекст

Сейчас:

- cookie `mb_session` (httpOnly, sameSite=lax, secure), Flutter — `Authorization: Bearer`;
- сессии в таблице `sessions`, TOTP-шаг в Redis/памяти;
- 2FA-билет в подписанной cookie на 5 минут;
- права сотрудников (`clients.view`, `orders.edit`, ...), IP-allowlist, обязательная 2FA;
- «только свои» сделки/заказы.

При выносе бэкенда каждый сервис должен понимать, кто пользователь, но не должен читать `sessions`
из чужой схемы.

## Решение

- **Оставляем свои сессии и cookie.** UX входа/2FA/сброса пароля не меняется.
- `platform` — единственный владелец `users`, `sessions`, прав, настроек безопасности.
- `web`/сервисы получают `UserContext` через introspection (`POST /internal/v1/session/introspect`)
  и **короткоживущий internal JWT** (EdDSA, 60 с, `aud` = сервис, scopes).
- JWT кэшируется в Redis 30–60 с по хешу сессии; JWKS platform кэшируется.
- Сервис проверяет JWT и **повторно** проверяет права на конкретный ресурс (defense in depth).
- Публичные вебхуки — без JWT; подпись провайдера + IP allowlist, если есть.
- Внутренняя сеть: `127.0.0.1`/private, HMAC `X-Internal-Token` для service-to-service; при
  multi-host — mTLS (отдельный ADR).

## Почему не Keycloak/OIDC

- Свои правила (IP, обязательная 2FA, «только свои», роли CRM) уже реализованы и протестированы.
- Миграция пользователей/паролей/2FA и экранов входа — дорого и рискованно.
- Keycloak — тяжёлый сервис (JVM, БД, темы), ещё одна точка отказа на 8 ГБ.
- OIDC можно добавить позже как внешний провайдер для B2B, не ломая текущие сессии.

## Последствия

- Нужны: JWKS endpoint, ключи EdDSA, кэш introspection, clock skew, rotation.
- Один лишний сетевой вызов на запрос (кэшируется).
- Все сервисы обязаны проверять `aud`/`exp`/`scopes`; нельзя доверять заголовкам `X-User-Id` без
  подписи.
- При утечке ключа — ротация и короткий TTL; сессии можно отозвать в platform.
