# ADR 0003. Данные: схема на сервис сначала, физическая БД — позже

**Статус:** предложено · **Дата:** 2026-11-05

## Контекст

Сейчас одна PostgreSQL-база, 54 таблицы, 17 схем по модулям. Между схемами — 66 внешних ключей,
больше всего на `identity.users` (39). `reporting` читает таблицы почти всех модулей.

Если сразу сделать database-per-service:

- 66 FK нельзя сохранить;
- `reporting` перестанет работать;
- потребуется синхронная репликация/саги до того, как появится опыт;
- миграции и бэкапы усложнятся в разы.

## Решение

1. **Волна 1:** одна БД, одна схема; владелец — `api`. `web` не имеет доступа к БД.
2. **Волны 2–4:** schema-per-service в той же БД:
   - `publishing`, `conversations`, `platform`;
   - таблицы переезжают через `ALTER TABLE ... SET SCHEMA`;
   - FK на чужие схемы снимаются (expand/contract), остаются идентификаторы.
3. **Только после этого** — физическое разделение БД для publishing/conversations/platform
   (отдельные базы/кластеры), если появится причина: изоляция нагрузки, бэкапов, доступа.
4. `core` остаётся в одной БД с `commerce`+`crm` до волны 6.

## Правила

- Одна таблица — один владелец. Чужой сервис не делает `SELECT`/`JOIN`.
- Ссылки — `uuid` без FK; целостность — события, саги, сверки.
- Миграции — у владельца схемы; общая миграция на две схемы запрещена.
- `reporting` остаётся в `core`; при выносе в `insights` получает read-модель, а не `JOIN`.
- `outbox_events` — у каждого сервиса своя (или общая таблица с `producer`, но лучше своя).
- Перед физическим разделением — тест, что сервис не обращается к чужой схеме (grep/линтер/рантайм-права).

## Почему не database-per-service сразу

- 66 FK и `reporting` — это не «детали», а основные сценарии.
- Одна БД даёт возможность отката и постепенного переезда.
- На одном VPS отдельные кластеры Postgres — лишняя память и обслуживание.
- Схема на сервис уже даёт ownership и позволяет потом физически разделить без переписывания кода.

## Последствия

- На волнах 2–4 в одной БД будут сосуществовать схемы разных сервисов; это временно.
- Нужны тесты, запрещающие импорт чужой схемы и прямые `JOIN`.
- Бэкап общий, пока БД общая; при разделении — у каждого свой.
