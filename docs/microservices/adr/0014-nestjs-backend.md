# ADR 0014. Бэкенд на NestJS (Fastify), переезд по контекстам

Статус: принято 26.11.2026 (решение владельца). Дополняет ADR 0009 (модульный монолит + воркеры) и ADR 0012 (API v1):
меняется только HTTP-слой и корень композиции, модули предметной области остаются.

## Контекст

После ADR 0013 веб живёт в `mybook-web` (Vercel) и ходит только в API v1. Бэкенд — `apps/api` (свой роутер над
контрактами), `src/server/*` (адаптеры сайта, 183 файла с `next/*` через прокладку `next-shim`), один корень
композиции `src/server/container.ts` (586 строк, лениво создаёт 19 модулей) и воркеры. Модули `src/modules/*` уже
устроены по DDD: `domain` (сущности, правила, ошибки, события) → `application` (сервисы сценариев, порты) →
`infrastructure` (Drizzle, хранилище, почта), наружу — фасад. Слабые места — не в модулях, а вокруг них:

- бэкенд всё ещё говорит на языке Next (`cookies()`, `headers()`, `cache()` из React, `NextResponse`) — без прокладки не
  запускается;
- вход, права, лимиты, язык и формат ошибок собраны в функциях `apiUser`/`api()`/`rateLimit()`, которые каждый
  обработчик вызывает сам (легко забыть проверку);
- один «божественный» контейнер: любой код достаёт любой модуль через `container()` (сервис-локатор), зависимости
  контекста не видны.

## Решение

Новый процесс **`apps/backend`** на NestJS 12 с адаптером Fastify. Переезд — **по ограниченным контекстам, по
стратегии «душитель»**: контекст переносится целиком (контроллеры + сборка его сервисов), под те же адреса
`/api/v1/*` и те же контракты; трафик переключается nginx-ом по префиксам, когда контекст прошёл сверку. Пока
контекст не перенесён, его обслуживает `mybook-api`.

### Слои и папки

```
apps/backend/src/
  main.ts                — запуск: Fastify, порт, корректная остановка
  app.module.ts          — корень: ядро + модули контекстов
  core/                  — сквозное, без бизнес-логики (одно место для каждого правила)
    config/              — переменные окружения: zod-схема → типизированный AppConfig
    kernel/              — общие порты ядра: UnitOfWork, Clock, RateLimiter, Logger (токены DI)
    http/                — контракт → маршрут Nest (@Endpoint), разбор входа и сверка ответа по контракту, ETag,
                           адрес клиента, язык запроса
    auth/                — SessionGuard (глобально; auth: none | user по контракту), @CurrentUser()
    errors/              — ApiError и фильтр: доменные ошибки, zod, HTTP → { error, code } на языке клиента
    rate-limit/          — @RateLimit() + guard поверх порта RateLimiter
    health/              — /api/v1/health
  legacy/                — антикоррупционный слой: единственная папка, где можно трогать src/server/container.
                           Отдаёт порты ещё не перенесённых контекстов (промокоды Ordering, уведомления Workspace)
  modules/<контекст>/    — Nest-модуль контекста: сборка его application-сервисов из domain/application/
                           infrastructure (src/modules/<контекст>), контроллеры, guard-ы политики доступа, презентеры
```

### Правила

1. **Предметная область не знает о Nest.** `src/modules/*/domain|application` — чистый TypeScript без декораторов.
   Nest-модуль контекста только собирает их (фабрики провайдеров) — так же, как раньше фасад, но с явными
   зависимостями. Порты — интерфейсы в `application/ports.ts`, адаптеры — в `infrastructure` или `legacy`.
2. **Контракт — единственный источник маршрута.** `@Endpoint(v1.reviewGet)` берёт метод, путь (`{id}` → `:id`) и
   `auth` из `@mybook/contracts`; вход разбирается схемами контракта, ответ вне прода сверяется с контрактом.
   Пути и схемы руками не дублируются (DRY), OpenAPI и Dart-клиент остаются верными.
3. **Проверки — декларативно.** Вход — глобальный `SessionGuard` по `auth` контракта; доступ к ресурсу — guard
   политики контекста (`ReviewAccessGuard`); частота — `@RateLimit()`. Обработчик контроллера — одна строка вызова
   сервиса и презентер.
4. **Ошибки.** Домен бросает свои ошибки (`DomainError` с кодом), HTTP-слой — `ApiError(status, code)`. Один фильтр
   переводит всё в формат сайта `{ error, code }` на языке запроса (статусы — общий реестр `src/i18n/api-errors.ts`,
   им же пользуется `mybook-api`).
5. **Без `next/*` и без сервис-локатора.** В `apps/backend/src` нельзя импортировать `next/*`, `react`, `@/server/*`
   (кроме `legacy/`) и `apps/api`. Это проверяет тест `apps/backend/test/boundaries.test.ts`.
6. **Внедрение зависимостей — явными токенами** (`@Inject(TOKEN)`), без `emitDecoratorMetadata`: сборка esbuild и
   vitest не генерируют метаданные типов, а явный токен ещё и делает зависимость от порта (интерфейса), а не от класса.
7. **Общий код презентации — один на оба процесса.** Пока контекст живёт в двух процессах, отображение
   (DTO, надписи) лежит в `src/modules/<контекст>/ui` и используется и `mybook-api`, и `apps/backend`.
8. **YAGNI.** Модули, guard-ы и порты появляются вместе с первым контекстом, которому они нужны. Вход сотрудника
   (`auth: "staff"`: роль, отключение, 2FA, список IP, права) появится с первым контекстом CRM; до тех пор
   `@Endpoint` отказывается регистрировать такой маршрут при запуске, чтобы права нельзя было пропустить.
9. **Общее ядро — одно на процесс.** UnitOfWork (outbox), Clock и RateLimiter в переходный период берутся из старого
   контейнера (`legacy`), чтобы события и лимиты не раздваивались. Когда переедут все контексты, ядро собирается в
   `core/kernel` напрямую, а `legacy/` и `src/server/container.ts` удаляются.

### Порядок переезда

| Шаг | Что | Готово, когда |
|---|---|---|
| 1 | Каркас (`core/*`, health) + контекст **Feedback** (`/api/v1/orders/{orderId}/review*`) | тесты e2e на Fastify inject, сборка в CI |
| 2 | Выкатка `mybook-backend` рядом (PM2, порт 3046; 3045 занят mybook-web), без трафика; сверка ответов с `mybook-api` | одинаковые ответы на проде |
| 3 | nginx: `location /api/v1/orders/…/review` → 3046 | неделя без ошибок |
| 4 | Остальные клиентские контексты: Identity (вход, вход сотрудника), Authoring, Ordering, Referrals, Support… | по одному, тем же порядком |
| 5 | CRM (`webCrm*`, `auth: staff`), вебхуки, `site-routes` | — |
| 6 | Воркер — Nest standalone-приложение (`NestFactory.createApplicationContext`) с теми же модулями; PDF остаётся дочерним процессом (ADR, pdf-worker) | — |
| 7 | Удалить `apps/api`, `src/server/container.ts`, `next-shim`, `legacy/` | все контексты на Nest |

## Последствия

- Плюсы: явные зависимости контекстов (видно из `imports` модуля), проверки входа и лимитов нельзя забыть, бэкенд без
  Next, тестирование через `Test.createTestingModule` с подменой портов, стандартная для TS-команд структура.
- Минусы: переходный период с двумя HTTP-процессами и общим ядром через `legacy`; +~3 МБ зависимостей
  (`@nestjs/*`, `fastify`, `rxjs`), запуск процесса на ~100 мс дольше.
- Отказались: переписать всё за раз (риск для прода, нет точки отката); Go/Rust (ADR 0011 — только для отдельных
  горячих сервисов); Express-адаптер (медленнее Fastify, без выигрыша).
