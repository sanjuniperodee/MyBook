# MyBooks: вынос бэкенда и разделение на сервисы

> Рабочая папка плана. Начало: 2026-11-05, ветка `refactor/microservices`.
> Живой статус — [PROGRESS.md](PROGRESS.md). Передача другому агенту — [HANDOFF.md](HANDOFF.md).

## Главное решение

MyBooks уже **модульный монолит** с чистыми границами: 17 bounded contexts, ноль импортов между модулями,
транзакционный outbox, Unit of Work, 4010 зелёных тестов. Это не «комок», который надо переписать, — это
хорошая основа, из которой можно аккуратно вынуть бэкенд.

Поэтому план — не «сделать 15 микросервисов за один спринт», а **поэтапно получить независимо
деплоящиеся сервисы там, где это даёт эффект**:

| Этап | Что получаем | Зачем |
|---|---|---|
| Волна 1 | `web` + `api` (переходное имя `core`: весь бэкенд в отдельном процессе) | Next.js больше не владеет БД; бэкенд можно катить отдельно |
| Волна 2 | `publishing` + `render-worker` | PDF/фото (до ~1 ГБ RAM) больше не роняют сайт |
| Волна 3 | `conversations` + `notifications` | WhatsApp/IMAP/АТС/бот изолированы, ретраи и очереди не в веб-процессе |
| Волна 4 | `platform` (identity/access/workspace) | Единая точка входа, сессии, права, настройки |
| Волна 5 | `ai` | Ключи, лимиты, стоимость и падения LLM не влияют на заказы |
| Волна 6 (опция) | `commerce` / `crm` / `insights` | Только если появится реальная причина: нагрузка, команда, релизный цикл |

**Целевая картина сейчас — 6 деплойментов + edge**, а не 15 сервисов:

```
web (Next.js BFF/SSR)
platform (identity + access + workspace)
core (ordering + sales + clients + automation + feedback + reporting)
publishing (authoring + production + render worker)
conversations (messaging + telephony + notifications + bot)
ai (LLM gateway)
```

`core` — это временный модульный монолит бэкенда. Его можно разнести на `commerce` и `crm` позже,
когда будут сняты внешние ключи между схемами и появятся саги. Полный target B (8 деплойментов) —
в [02-target-architecture.md](02-target-architecture.md).

## Что уже готово

- **Границы модулей держатся линтером и тестом** `tests/architecture.test.ts`; нарушений 0.
- **Доменные события** уже идут через `outbox_events`, а не «в памяти после коммита».
- **Сценарии** уже в application-сервисах, а не в страницах.
- **Фронтенд** уже почти не ходит в БД: `app/` и `components/` получают данные через `container()`.

Главные блокеры, которые план снимает по порядку:

1. **643 вызова `container()` в 202 файлах** — это шов. Меняем транспорт с «в процессе» на HTTP,
   не меняя сигнатуры и не трогая разметку.
2. **66 внешних ключей между схемами** (например, `sales -> identity` — 13). Пока они есть,
   базы нельзя разделить. Снимаем в волнах 2–4.
3. **`reporting` читает все схемы сразу** (заказы, сделки, книги, чаты, звонки). Это последнее,
   что можно выносить; до этого отчёты живут в `core`.
4. **Один VPS 4×8 ГБ, общий с другими сайтами**, PM2, nginx, PDF до ~1 ГБ. Полный набор сервисов
   может потребовать +4–8 ГБ RAM или вторую машину. Это отдельное решение, а не «бесплатно».

## Как сохраняем фронтенд

Визуально не меняется **ничего**: ни разметка, ни CSS, ни тексты, ни URL. Меняется только источник
данных на сервере.

Три уровня страховки:

1. **Существующий стенд** `scripts/visual/check.sh` — PDF и HTML книги, 192 ключа, попиксельная сверка.
2. **Playwright-стенд** для админки и клиентских страниц: 20 маршрутов, desktop/mobile, seed-данные,
   фиксированные даты. Добавлен в M0.3 — `tests/visual/pages.README.md`.
3. **Parity-режим**: BFF умеет звать и старый in-process `container()`, и новый HTTP-бэкенд,
   сравнивает ответы и пишет расхождения в лог. Включается флагом, не влияет на пользователя.

Плюс контрактные тесты DTO: форма ответа HTTP-сервиса должна совпадать с формой, которую сегодня
получает страница. Это ловит дрейф данных, который скриншоты могут не заметить.

## Инфраструктура: что нужно, а что нет

| Технология | Нужна? | Когда | Зачем |
|---|---|---|---|
| **Redis 7** | Да | Волна 1–2 | Лимиты, идемпотентность, прогресс рендера, очереди BullMQ, presence/SSE. Сейчас опционален, с несколькими процессами становится обязательным |
| **BullMQ 6** | Да | Волна 2 | PDF, превью, фото, письма, исходящие WhatsApp, AI-задачи: ретраи, backoff, DLQ, прогресс |
| **NATS JetStream 2.x** | Да | Волна 2–3 | События между сервисами. Легче RabbitMQ, в отличие от Kafka не требует отдельной команды эксплуатации. Outbox остаётся источником истины |
| **PostgreSQL 16** | Да | уже есть | Схема на сервис, потом отдельные БД. PgBouncer — при росте соединений |
| **Yandex Object Storage (S3 API)** | Да, решено | Волна 2 | Бакет `mybooks`, endpoint `storage.yandexcloud.net`. Фото, PDF, вложения; ключи вне git — [07-storage-s3.md](07-storage-s3.md) |
| **OpenTelemetry + Prometheus/Grafana** | Да | Волна 1–2 | Без трассировки распределённый бэкенд не отлаживается |
| **Sentry** | Желательно | Волна 1 | Ошибки фронта и сервисов |
| **Meilisearch** | Позже | Волна 6 | Если понадобится поиск с опечатками. Сейчас — Postgres FTS + `pg_trgm` |
| **Elasticsearch/OpenSearch** | **Нет** | не сейчас | Слишком тяжёл для 8 ГБ; для 54 таблиц и сотен тысяч строк хватает Postgres. Вернуться при логах/аналитике на десятки миллионов документов |
| **Kafka / RabbitMQ** | **Нет** | — | Объём — тысячи событий в сутки. NATS + outbox закрывают с запасом |
| **Kubernetes / service mesh** | **Нет** | — | Один VPS, PM2/Compose. K8s здесь — операционная роскошь |
| **Keycloak / OIDC-провайдер** | **Нет** | — | Свои сессии, 2FA, права сотрудников уже работают; миграция дороже пользы |
| **GraphQL / gRPC** | **Нет** | — | HTTP/JSON + OpenAPI достаточно; gRPC добавит кодогенерацию и отладку без выигрыша |

Подробно — [04-stack-decisions.md](04-stack-decisions.md).

## Правила работы

- **Не менять UI без явного запроса.** Ни разметку, ни стили, ни тексты, ни URL. Визуальная сверка — гейт.
- **Не деплоить в прод без явного «да» пользователя.** Ветка, PR, проверки — можно; прод — только по команде.
- **Одна волна — одна ветка, маленькие PR.** Не смешивать переезд файлов, смену данных и новую функциональность.
- **Каждая задача обновляет [PROGRESS.md](PROGRESS.md)**: статус, что проверено, следующий шаг.
- **Новые инфраструктурные технологии — только через ADR.** Kafka, Elasticsearch, Kubernetes, GraphQL, gRPC, второй брокер — не появляются «по ходу».
- **Сначала контракт, потом перенос.** Для каждого сервиса: OpenAPI/схема события → тест → реализация → переключение флага → наблюдение.
- **Секреты не в репозитории.** `.env` — только локально/на сервере; в docs — имена переменных, не значения.
